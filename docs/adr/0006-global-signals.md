# ADR 0006: MCPグローバルシグナル

## Status

採用。2026-10-13。登録表の基盤を実装。公開ツール・監視・寿命管理は後続項目です。

## Context

条件監視は待機要求より先に開始できる必要があります。プロセス全体の登録表でも、別のAIセッションや次のロック取得へ登録が流用されないことが必要です。

## Decision

register_signalはMCP管理ツールと共通操作の両方に接続します。受付で所有者と取得ロックの内部IDを固定し、共通操作はキューの所有者を引き継ぎます。OperationExecutionContextへ秘密トークンを保存しません。条件の種類ごとの検証・初期評価・監視開始はISignalConditionProviderへ委譲し、開始完了と初期評価の通知を確認してから応答します。監視開始はOperationTimeoutSecondsを上限とします。監視寿命は呼出し元HTTP接続の寿命から分離します。

未実装の監視種類はSIGNAL_CONDITION_UNSUPPORTEDで登録を作成しません。P13-02時点では監視プロバイダーはまだ登録しておらず、各種類は後続P13-06～P13-12で接続します。構造不正、対応する種類のスキーマ違反、保持数超過、監視開始失敗を区別します。成立後の監視は一回限りで取り消します。

各MCPロック取得へ秘密でない内部LockIdを発行し、更新では同じID、再取得では新しいIDとします。シグナルは所有セッションとこのLockIdに結び付けます。表へロックトークンの平文・ハッシュを保存しません。所有者の照合後にキューの現在ロック世代を再検証し、両者の排他ロックを同時には保持しません。

sig_形式のIDで条件JSON・期限・pending/signaled/expired/invalidated/unregistered状態・成立時刻・観測結果を保持します。成立は一度だけ記録して待機で消費しません。条件は64KiB、観測結果は16KiBまでとし、設定MaxSignalsを成立済みも含む有効登録へ適用します。終了登録は結果保持期間と最大1000件の上限で保持し、終了理由を区別します。待機の通知は継続処理を同期実行しないTaskCompletionSourceとします。

## 代替案と不採用理由

- セッションIDだけで所有する: ロック再取得後に古い登録を誤って利用できます。
- キューの排他下で登録表を操作する: 監視コールバックの逆方向ロックでデッドロックになります。
- 条件を任意プログラムとして保存する: 監視条件の検証・資源制限ができません。

## 影響範囲

シグナル管理ツール・単体/JSON/Aloeの待機・MCPロック失効と解放へ適用します。登録表基盤だけではシグナルツールを公開しません。

## セキュリティ条件

WebDriver Classicの選択タブ・フレームは接続全体の状態です。BrowserOperationGateを通常のbrowser.*・dom.*操作の開始から完了まで、およびDOM監視の一回の読み取り全体へ適用します。HTTPコマンド単位の排他では選択と要素操作の間に他の監視が割り込むため不十分です。register_signal/wait_for_signal自体はこの排他を保持せず、待機中の監視を妨げません。DOM監視は登録時の文書ルートとネイティブフレームを固定し、その文書内でだけCSSを毎回検索します。文書入替え・フレーム消失は別文書へ追従せず失効します。背景監視もWebDriverのコンテキスト選択を行うため、ブラウザ側の選択状態が変わる可能性があります。外部操作による一時的なBFCache往復を完全には検出できない制約は既存DOM参照と同じです。

他所有者・別ロック世代からの参照はSIGNAL_ACCESS_DENIEDです。監視者は登録表の固定Entry参照で通知し、IDを再対応しません。条件比較本文・観測本文・所有者情報・内部LockIdをログへ保存しません。

## 運用条件

JSONバッチのsignalKeyは要求ごとのSignalBatchBindingsへ結び付け、登録成功後のsignalIdを後段へ渡します。受付前に全操作を検証し、ASCII英数字とアンダースコア1～64文字、重複登録なし、定義後の参照のみ、signalIdとの排他的指定を確認します。単体操作はsignalIdを使い、同じ要求IDの再送は既存の受付・指紋規則に従います。単体とバッチの両方でシグナル操作へ所有者と取得ロック世代を渡します。

unregister_signalはMCP管理ツールと共通操作に接続し、所有者と取得ロック世代を確認して登録をunregisteredへ変更します。未成立で待機中の要求へSIGNAL_UNREGISTEREDを通知し、監視の取消とDisposeAsyncの完了を待って応答します。保持中の同じ解除IDへの再解除はalreadyUnregistered:trueです。未知ID・他所有者・期限切れ・監視障害を別のコードとし、期限切れ等で既に終了した登録でも監視の後処理を試みて元の終了理由を返します。成立が解除より前に記録されていた待機では、最初に記録された成立通知を利用します。

wait_for_signalは単体MCPでも共通操作でも同じFIFOキューで実行し、timeoutMs:0～300000を受けます。要求の所有者・取得ロックの世代と登録を照合し、一回限りの成立通知を待ちます。待機期限と成立記録はStopwatchの単調時刻で比較し、期限までに記録された成立を優先します。通常時間切れは成功結果status:timeoutであり、要求・操作の上限や取消は既存キューの中断規則で扱います。未知ID・期限切れ・解除・監視障害を区別します。0は開始時点の判定です。待機はシグナルを消費・再武装しません。登録期限は既存のUTC期限を使用し、待機中も短い通知待ちで確認します。

揮発性データで再起動後は失効します。期限はUTCの時刻で保持し、時計変更の影響はOS時計に従います。SignalLifetimeServiceが200ms周期で期限と現在のロック世代を確認し、HTTP要求がなくても監視を整理します。期限切れはSIGNAL_EXPIRED、ロック終了・受付停止・強制解除はSIGNAL_UNREGISTEREDとして登録を終了します。成立済みは監視だけを止め、期限まで結果を保持します。整理開始は次回周期で、OSの実行遅延と監視解放待ちは加算されます。キューの排他下から登録表を呼び出さず、開始中の解除は開始取消と資源生成完了の通知を利用して生成後に解放します。本体終了時にも監視停止を待ちます。

## 実装・検証・文書への対応

window.stateは参照に固定したウィンドウのexists/active/minimized/maximizedを設定間隔で読み取ります。消失待ちのexists:falseは、失効通知より先に成立を評価します。control.stateはUIA要素のenabled/visible/focused/toggle/selectedを既存MTAドライバで検証して読み取ります。visibleはIsOffscreenの反転であり遮蔽とは別です。画像参照や未提供パターンは非対応として拒否します。

window.openedは既存ウィンドウの基準一覧を取得してからWinEventフックを設置し、設置後のCREATE/SHOW通知を専用スレッドとメッセージループで処理します。既存参照IDを除き、プロセス名・設定の実行パス・タイトルを比較します。通知キューは256件で、超過は監視障害とし、ポーリングへ代替しません。短命な対象や通知後のタイトル変化の検出は保証しません。フックとコールバックの生存期間、およびメッセージループは[MicrosoftのSetWinEventHook仕様](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook)に従います。

SignalRegistryとキューのロック世代検証を実装し、全体ビルドと仕様・計画・進捗を更新します。競合・タイマー・実機監視は未検証です。
